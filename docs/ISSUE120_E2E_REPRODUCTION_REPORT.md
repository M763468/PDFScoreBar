# Epic #120: E2E Pipeline Reproduction and False Negative Analysis Report

## 1. 調査の背景と目的
HANDOFF.md に記載された「パイプライン前半処理（PDFからの画像変換、OMR推論、Hybrid Consensus等）を含めたE2Eパイプライン実行による精度検証」において、過去のベースライン（`scoring_input_eval2_v12` 相当）と同じ中間生成物（シード）が生成できておらず、精度（TP=3580, FN=1, FP=0）が維持できない問題の調査を行いました。

本レポートでは、v12 ベースラインのシードがどのように生成されていたかの全貌と、それを現在の E2E パイプライン上で再現する過程で判明したパイプラインの課題、および現在の False Negative (FN) の真の発生原因について時系列で記録します。

---

## 2. v12 ベースライン生成過程の解明（初期調査）
過去のスクリプト（`tools/repro_accuracy/reproduce_clean_seed_v12.py` および GT 作成ツール）を解析し、v12 のシードが以下の特異な条件で生成されていたことが判明しました。

1. **Hybrid Consensus の UNION 結合**:
   v12 では、初期候補を最大化するために Baseline, SR, OMR-DLN の 3 モデルの出力をすべて `UNION`（論理和）で結合し、IoU > 0.8 で重複排除していました。現在の E2E のデフォルトは `INTERSECTION` であり、かつ直近の実行では OMR-DLN が計算コスト削減のためスキップされていました。
2. **入力画像解像度 (DPI) の相違**:
   v12 では事前に抽出済みの 360 DPI 相当の画像群 (`data/evaluation2/images`) が使用されていました。現在の E2E は PDF から 300 DPI で動的にレンダリングしていたため、座標系が完全に一致しない状態でした。
3. **マスク画像の形状**:
   v12 の生成スクリプトは、デバッグ用の**「線」だけの五線譜マスク (`debug_3_staff.png`)** をフィルタリングに利用していました。一方、現在の E2E パイプラインは動的に「領域」としての五線譜マスクを生成します。

---

## 3. `min_paper_overlap_ratio` 問題の浮上と真相
上記の v12 設定を E2E に移植して実験を行った際、**生成された数千の候補が、ヒューリスティックフィルタ（`filter_probe_candidates`）によってほぼ全て（数個〜数十個まで）破棄される**という現象に遭遇しました。

調査の結果、以下の事実が発覚しました：
* **破棄の原因**: フィルタの一つである `low_paper_overlap`（紙領域との重なり割合が閾値未満）が原因でした。小節線は黒インクの塊であり、タイトな Bounding Box で囲むと「白紙（背景）」の割合が低くなるため、現在のデフォルト閾値（`0.6` = 60%）では全て不合格となります。
* **過去 (v12) で通っていた理由**: 過去に v12 を生成したスクリプト（`suggest_candidate_drops.py`）を遡って解析した結果、引数として `min_paper_overlap_ratio=0.6` は指定されていたものの、**実際のコード内部ではこの変数が一度も使用されていない（実装漏れにより無効化されていた）** ことが判明しました。

この真相に基づき、E2E での再現実験では `min_paper_overlap_ratio: 0.0` と設定し、過去の実質的な無効化状態を再現しました。

## 4. E2E 再現実験（V9 run）と GT（正解データ）カバレッジの検証
上記の全調査結果を踏まえ、E2E パイプラインを以下の設定（V9）で実行し、`Va_Prokofiev_Symphony1` の 3 ページを対象に検証を行いました。

*   入力: 360 DPI 画像 (`data/evaluation2/images`)
*   Hybrid: `UNION` モード、OMR-DLN を有効化 (`use_omr: true`)
*   フィルタ: `min_paper_overlap_ratio: 0.0`

### 4.1 シード生成段階における GT カバレッジ（Recall）と評価の修正
生成された中間データが「正解（Ground Truth = GT）の小節線」を本当に捉えきれているのかを、IoU > 0.1 の緩い重なりで検証しました。

| ページ | GT の総数 | 生成シード（未フィルタ）に含まれる GT | ヒューリスティックフィルタ通過後の GT |
| :--- | :--- | :--- | :--- |
| page_001 | 85 個 | 81 個 | 81 個 |
| page_002 | 80 個 | 79 個 | 79 個 |
| page_003 | 80 個 | 76 個 | 76 個 |
| **合計** | **245 個** | **236 個 (96.3%)** | **236 個 (96.3%)** |

**【重要】結果の評価の修正**:
当初、96.3% のカバー率をもって「シード生成は成功している」と評価しましたが、これは誤りでした。過去のベースラインの評価精度は **FN=1（全データセットで取り逃しが1個のみ）** であり、シード生成の段階で 3.7% も GT を取り逃している現在の状態は、明確な **シード生成フェーズの劣化（False Negativeの発生源の一つ）** を意味します。シード生成の段階で取り逃した GT は、後段の CNN がどれだけ優秀でも絶対に回復できません。

### 4.2 CNN スコアリングによるさらなる False Negative の発生
シード生成で生き残った 236 個の GT 候補に対する CNN のスコア分布は以下の通りでした。

| ページ | フィルタ通過 GT | CNN スコア >= 0.1 (合格) | CNN スコア < 0.1 (不合格・破棄) |
| :--- | :--- | :--- | :--- |
| **合計** | **236 個** | **215 個** | **21 個** |

**結論**: パイプライン前半を運良く通過した正解画像に対してすら、**CNN モデルが 0.1 未満の低いスコアを割り当ててしまい、21 個の False Negative が直接的に生み出されている**ことが確認されました。

### 4.3 「後段の NMS やヒューリスティクス」について
CNN スコアリング（確率 0.1 以上で足切り）を通過した後も、パイプラインの最終出力に至るまでに以下の処理が行われます。これらも残りの FN を生み出す要因です。

1.  **NMS (Non-Maximum Suppression)** (`src/pipeline/steps/cnn_scoring.py` の `_apply_nms`等): 同一の小節線を指している複数の重複枠のうち、最もスコアが高いものだけを残して他を消去する処理。ここで誤った（少しズレた）枠の CNN スコアが、GT にピタリと合致する枠より高いと、正しい枠が NMS によって「重複」として消去されてしまいます。
2.  **後処理ヒューリスティクス** (`tools/re_evaluate_global.py` の `greedy_barline_match` のルールや、パイプライン内部の最終フィルタ): 空間的な整合性チェック。例えば、五線譜の段落（システム）から大きく外れて孤立している候補を、ノイズとみなして削除する処理です。

---

## 5. 最終的な結論と今後のアクション
現在の E2E 全体で精度が低下し、過去の FN=1 を再現できない原因は、特定の箇所ではなく**パイプラインの複数のフェーズに跨って存在**しています。

1. **シード生成フェーズ**: すでに GT の 3.7% を取り逃している。
2. **CNN スコアリングフェーズ**: さらに GT の約 9% に合格スコア（0.1）を与えられずに破棄している。
3. **NMS/後処理フェーズ**: （上記を通過した候補に対して）さらに競合や空間判定で破棄している可能性。

**今後のアクション（次セッションの目標）**:
最終目標は **TP=3580, FN=1, FP=0** の完全復元です。
次セッションでは、まず「なぜシード生成段階で GT が漏れるのか」または「なぜ CNN が GT に対して低いスコアを出すのか」の具体的な FN サンプルを特定し、それらを救済するための抜本的な調査と実装の修正を開始する必要があります。
