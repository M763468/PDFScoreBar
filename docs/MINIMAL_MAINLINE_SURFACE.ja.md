配布候補は、[MINIMAL_MAINLINE_SURFACE.json](MINIMAL_MAINLINE_SURFACE.json) にある **118個の追跡ファイル**です。内訳は `src/` 配下の89ファイルと、本番の config・モデル・Docker・パッケージのファイル、パッケージに含める利用者向け補正アプリケーション、最小限の利用者向け文書、チェックアウト用の ignore 規則です。正確な配布物は、`runtime_bundle_patterns`、`distribution_support_patterns`、`distribution_metadata_patterns` の和集合です。生成される `DISTRIBUTION_PROVENANCE.json` は、ソースの識別情報、dirty の状態、配布する各ファイルのハッシュを記録します。

この選定は Issue #100 と #409 で定め、#410（リリース候補 RC4、PR #442）で初めて `main` へ昇格しました。`develop` の変更が `main` に届くのは、[ブランチ方針](BRANCH_POLICY.ja.md)に従った後のリリース昇格を通じてだけです。過去の各候補サイズでの受入の証拠は、[#409 の受入履歴](releases/issue409/ACCEPTANCE_HISTORY.md)（英語）に残しています。

## 選定の理由

以前の #392 の一覧は、依存関係の閉包でした。この監査は製品としての責務に基づいて選びます。その責務とは、PDFの入力、番号付きの最終PDF、利用者のレビュー、記録した補正、補正済みの最終PDF、確認可能なランタイム・モデル・入力の識別情報です。選定したSRキャッシュのモジュールは、任意で有効にするコンパイラキャッシュの契約を実装しています。workerがキャッシュを選んだ場合にだけimportしますが、ランタイムの一式に含めます。キャッシュを設定しない場合のSRの実行経路は変わりません。sourceの並行処理のモジュールは、保守対象のバッチSR検出器が、汎用の1 workerの既定値でもimportするため含めています。2 workerを選ぶことは、引き続き環境ごとの任意の設定です。

| 選定したカテゴリ | 具体的な配布の理由 |
| --- | --- |
| `src/common`、`src/homr_runtime` | モデル・リソースの解決、本番の幾何、固定した HOMR の推論 |
| `src/measure_numbering` | グループ化、MMR/OCR、番号付け、オーバーレイの描画 |
| dense の本番 `src/pipeline` | PDFのジョブ、検出器・SRのworker、候補の処理、補正、最終出力、来歴 |
| 2つの正規の config | dense のアルゴリズムの基本設定と、固定した保守対象の HOMR プロファイル |
| 3つのモデルファイル | CNN とダウンロードの契約、検証済みの外部 OMR-DLN の契約、追跡している本番の MMR チェックポイント |
| 本番の Docker ヘルパーとメタデータ | クリーンなビルド、互換性・プリフライト、通常のPDFと補正の操作 |
| `tools/review_correction` の11ファイル | サポートする利用者向けサーバー、パッケージ・状態のアダプタ、ローカルの英語・日本語UI |
| README と利用者ガイド | インストール、実行、レビュー・補正、トラブルシューティング、資産の所有 |
| 配布のメタデータと ignore 規則 | 監査可能な正確な配布の選定。生成されるランタイムのファイルを Git に入れない |

既存のランタイムの項目は、すべてこれらの責務に照らして見直しました。GTのマッチングは、共有パッケージのexportと本番の幾何の呼び出し側から、`src/common/barline_evaluation.py` を通じて不必要にimportされていました。変更していない幾何の関数・定数は現在 `barline_geometry.py` にあり、評価用のexportは develop の呼び出し側のために遅延importのままです。評価モジュールは除外しています。閾値やモデルのバイト列は変えていません。

利用者向け補正アプリケーションを一律に除外していた以前の扱いは、**配布**の境界で取りやめました。その運用に必要な11ファイルを個別に選定しています。`acceptance.py` と `browser_acceptance.cjs` は引き続き開発用の検証です。利用者向けアプリとGT用アプリはすでに独立しており（#393）、GTのサーバーや資産は含めていません。保守対象の番号レイヤーのモジュールは、ランタイムのソース一式に分類しています。Issue441 の探査・出力・検証のスクリプトとブラウザの受入ランナーは開発用の検証として残し、番号の所有、チェックポイント、返却されたPDFの安全性のテストは保守対象の契約です。それらの非公開の入力は配布しません。

配布物がサポートするのは maintained_original/dense_full_pipeline だけです。develop 専用の探査画像、幅の広い候補の分割、単独の番号付けCLI・オーバーレイは除外しています。それらを有効にする経路は develop では引き続き機能します。遅延importする過去の互換経路と評価用のexportも、manifest に明示した理由とともに除外したままです。

ローカルのジョブのアダプタは、v1 エンジンのレビュー出力を利用者向けアプリケーションへ橋渡しもします。エンジンは意図的にファイルシステム上のソースの参照を取り除き、作業ツリーの名前を変えます。アダプタは、変更しない保持済みの manifest の隣に、場所を移した別の `local_manifest.json` を作り、ローカルの handoff をそれに結び付け、結果の成果物のハッシュを更新します。元の manifest のハッシュは引き続き確認でき、エンジンのAPIと補正のスキーマは変わりません。レビューの起動時には、検出器の推論なしに、保持済みのローカルのジョブについてこの橋渡しを用意できます。

## 失敗時の契約

以前の監査では、選定した低レベルの入口が `precomputed_sr` がない場合も受け付けていたため、ページ単位のSRを残していました。その条件は別の互換モードを選ぶもので、バッチが失敗したときに自動で再試行したことはありません。現在の本番の契約の既定は `batch_required` です。事前計算したSRがない、明示的に null、または不正な場合は、HOMR が始まる前に失敗します。保守対象のソースページのworkerとバッチのヘルパーは、ベースラインの推論の前にこれを検証します。develop の呼び出し側は、`sr_mode=page_local` を明示的に指定する必要があります。過去のバッチ以外のソース生成はこのモードを書き込みます。develop には両方のモードが残りますが、配布物でサポートするのはバッチSRだけです。

| ケース | 分類と現在の挙動 |
| --- | --- |
| 汎用のSRが失敗時に元の画像を返す | develop の過去の互換性: `apply_advanced_sr(strict=False)` を残しています。検証済みのページ単位のSRは明示的に `strict=True` を使います。依存関係・モデル・初期化・推論のエラーは伝播し、出力は保存や完了の記録の前に正確に x4 である必要があります。バッチSRはすでに例外を出し、形状を確認します。 |
| 事前計算したSRがない | develop での明示的なページ単位の実行モード。本番では失敗します。`current_sr_worker.py` とその依存先の `common/preprocessing.py` は配布物からだけ除外し、サブプロセスの参照は任意と宣言しています。 |
| HOMR/OMR の JSON や座標が不正 | 空の予測ではなく破損として扱います。正規の合意処理は厳格なローダーを使い、成果物のパスとともに例外を出します。過去の開発用ローダーの呼び出しは、明示的に `strict=False` を使います。 |
| 有効な空のリスト、または空の予測のリスト | 通常の検出ゼロです。厳格なローダーも `[]` を返します。 |
| 端で切れて幅・高さがゼロのボックス | `int` への変換を含め、既存の HOMR/OMR の出力の契約を保ちます。上下・左右が逆の範囲は引き続きエラーです。 |
| 任意の救済シードがない | 汎用・develop でのシードなしの使い方は、`require_seed_files=False` で引き続きサポートします。 |
| 必須の救済シードがない、または破損している | 正規の dense の救済は `require_seed_files=True` を設定します。ファイルがない場合はページの識別情報と探索したパスとともに、JSONが不正な場合はそのパスとともに例外を出します。既存の有効な空のシードは引き続きサポートします。 |
| `scan_x_domain_mode=staff_mask` を明示したのに五線マスクがない、または読めない | 必須のマスクは、探査検出の前に、ページとパスの情報とともに失敗として扱います。`staff_mask_or_existing_boxes` と `full_width` は、既存の任意のマスクの挙動を保ちます。デコードした結果がすべてゼロのマスクは、引き続き有効な入力です。 |

ソースファイルは残しています。数値のアルゴリズム、モデル、閾値、座標の丸め、合意の順序、通常の成功したSRの出力は変えていません。失敗時の挙動は意図的に厳しくしています。影響を受けるworkerは停止し、エンジンのジョブは FAILED を返し、通常の最終・レビューの成果物は公開されません。既存の v1 の公開エンジンのスキーマは変わりません。失敗の注入と、実際の通常のワークフローの受入は、[#409 の受入履歴](releases/issue409/ACCEPTANCE_HISTORY.md)（英語）に記録しています。

## develop 専用の分類

3つの正確な一覧に含まれないものは、すべて `develop` に残ります。次を含みます。

- すべての評価・GTのコーパス、`data/**`、`datasets/**`、テストとfixture、CI、回帰・評価の全体のツール。サポートする製品の運用にはどれも必要ありません。
- Stage-E の再現用のイメージ、プロファイル、経路、`tools/issue120/**`。過去の HOMR の Dockerfile。実験と、ignore したログ配下の Issue の証拠。
- GTのラベル付け直し・学習のツール、レビューの受入ハーネス、広範なスクリプトや Makefile の自動化、リポジトリの一覧・チェッカー、抽出のツール。
- エージェント・Codex・Gemini の自動化、Skill、生成された Graphify の出力。
- アーキテクチャ、検証、サービス設計、履歴、調査の文書。

ソースの除外と、config・テストの役割は、JSON に個別に記録しています。既定の除外規則は、将来選定されないファイルにも適用されます。保守対象の開発用であることは、配布対象であることを意味しません。抽出によって、保持している開発の証拠が削除されることはありません。

## 文書の読者

| 読者 | 配布での選定 |
| --- | --- |
| 利用者・配布 | 英語と日本語の README と USER_GUIDE: ビルド、実行、レビュー・補正、トラブルシューティング |
| 運用者・リファレンス | manifest とモデルの識別情報、プリフライトと結果の来歴 |
| 開発者 | アーキテクチャ、環境、エンジンの契約、検証方針、一覧。除外 |
| 履歴・調査 | リファクタリング・Issue の文書と、受け入れた実験。除外 |

manifest の読者のパターンは責務を説明するもので、追加のファイルを選ぶものではありません。利用者ガイドが、運用の唯一の手順書です。以前の開発者向け README にあった、除外したアーキテクチャ・エージェントの文書へのリンクは、配布の入口から取り除いています。

## 抽出と確認

develop から実行します。

```bash
python3 tools/check_repository_surface.py
python3 tools/materialize_distribution.py materialize /tmp/pdfscorebar-candidate
python3 tools/materialize_distribution.py check /tmp/pdfscorebar-candidate
```

開発用のチェックアウトの外にある新しいディレクトリを使います。materializer は、シンボリックリンク、パスの遡り、重複、存在しない入力、既存の出力ディレクトリを拒否します。正確に選定したファイルだけをコピーし、ファイルのハッシュとソースの識別情報を保存してから、隔離したツリーを確認します。チェッカーは、候補の中に Git や宣言していない開発用ファイルを必要としません。開発側のチェッカーは外から候補を調べます。確認の対象は、ローカルのimport、既知のサブプロセスのモジュール参照、文書・UIのリンク、内容のハッシュ、予期しないファイルです。これらは実際の Docker・PDF・アプリケーションの受入を補うもので、数値の精度を証明するものではありません。

USER_GUIDE に従い、`python3 docker/distribution.py build`、`preflight`、`run`、`review` を**候補から**実行します。必要な受入は、クリーンな本番のビルド、正規のプリフライト、PDFから最終出力まで、レビュー・保存・補正済みの最終出力への適用、両方のUI言語、GT・開発・再現用の資産に依存しないこと、確認可能な来歴です。証拠は develop の作業中の Issue のログのルート（`logs/issue<N>/`）に置きます。幾何・アルゴリズム・モデルのバイト列が変わらなければ、検出器の全体評価は不要ですが、範囲を絞った幾何の互換性と本番のスモークは引き続き必要です。必要な配布のゲートがすべて合格するまで、候補を受け入れたと報告しないでください。
