## 配布物を入手する

`main` は安定版の最小配布ブランチ、`develop` は開発統合ブランチです。`develop` にマージされた変更は、別途リリース昇格されるまで `main` に現れません。このガイドの更新も昇格後に `main` に反映されます。検証済みの展開済み配布物が手元にある場合は、clone の代わりにそのルートディレクトリを使用してください。

Linux ホストで、ディストリビューションのパッケージマネージャーか [Git のインストール手順](https://git-scm.com/install/linux)を使って Git を導入します。次に端末を開いて実行します。

```bash
git clone --branch main --single-branch https://github.com/M763468/PDFScoreBar.git
cd PDFScoreBar
```

以降のコマンドはすべてホスト上のこの配布ルートで実行します。Git checkout は Git で確認できます。一方、展開済み配布物には来歴メタデータが含まれます。現在の `develop` の文書を使う場合は意図的に開発 checkout を使用してください。これは安定版配布物ではありません。

## ホストを準備する

NVIDIA GPU と互換性のある NVIDIA ドライバーを備えた Linux を使用します。[NVIDIA のドライバー導入手順](https://docs.nvidia.com/datacenter/tesla/driver-installation-guide/choose-an-installation-method.html)とディストリビューションの案内に従ってドライバーを導入してください。[Linux 用 Docker Engine](https://docs.docker.com/engine/install/) を導入してデーモンを起動し、[NVIDIA Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html) を Docker 用に導入・設定します。Linux ディストリビューションと権限に合った手順に従ってください。これらのリンクは、すべての OS や GPU の組み合わせが PDFScoreBar でサポートされることを意味しません。

ホストの Python 3.12 以降をディストリビューションのパッケージまたは [Python のダウンロード](https://www.python.org/downloads/)から導入します。`python3` が古いバージョンを指す場合は、以下のすべてのコマンドで 3.12 以降の実行ファイルを代わりに使用してください。

ホストと Docker へのアクセスを確認します。最後のコマンドは必要に応じてテスト用イメージをダウンロードします。

```bash
python3 --version
nvidia-smi
docker info
docker run --rm --runtime=nvidia --gpus all ubuntu nvidia-smi
```

最後のコマンドは NVIDIA の[サンプルワークロード](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/sample-workload.html)に従っています。ホストの `nvidia-smi` が失敗する場合は、まずドライバーと GPU を確認します。ホストでは動作してコンテナーでは失敗する場合は、toolkit の導入、Docker ランタイム設定、デーモンの再起動を確認します。`docker info` が接続できない場合は、デーモンを起動するか、[Docker の Linux インストール後の手順](https://docs.docker.com/engine/install/linux-postinstall/)でソケットの権限を確認します。`docker` グループへの所属は root 相当の権限を与えるため、選択の意味を理解したうえで有効にしてください。

ランチャーは現在のユーザーとして Docker を呼び出します。コンテナーが書き込むファイルの所有者はコンテナーユーザー（多くの場合 root）になることがあるため、出力先のファイルシステムに空き容量があり、結果を読み取り・保持できることを確認してください。所有権については、無関係なファイルを再帰的に変更せず管理者に相談してください。

これらの確認はホストとコンテナーのアクセスを確認するものであり、PDFScoreBar との互換性を保証しません。ビルドにはネットワーク接続と、イメージレイヤーおよびモデルを保存する十分なディスク容量が必要です。処理にもレンダリング済みページと保持する成果物のための空き容量が必要です。最低 VRAM 容量は規定していません。

## 要件とインストール

主なインストール方法は、NVIDIA GPU、動作する NVIDIA Container Toolkit、ホストの Python 3.12 以降、および CUDA／モデルイメージとレンダリングされた PDF ページに十分なディスク容量を備えた Linux 上で Docker を使用する方法です。ビルドにはネットワーク接続が必要ですが、通常の実行はオフラインです。ランタイムイメージには Python 依存関係、保守対象の [HOMR](https://github.com/liebharc/homr) モデル、[Real-ESRGAN](https://github.com/xinntao/Real-ESRGAN) モデル、ハッシュ検証済みの小節線 CNN が含まれます。配布物には MMR チェックポイントが含まれます。

配布物のルートで実行します。

```bash
python3 docker/distribution.py build
```

別のイメージを選択するには、コマンドの前に `--image YOUR_TAG` を指定します。ランチャーは本番アセットラベル、不変のイメージ ID、ランタイム互換性フィンガープリントを確認します。ビルドに成功すると、ソースコミットとフィンガープリントのラベルがイメージに保持されます。イメージはビルドされたランタイムのひな形であり、各コマンドで作成される一時コンテナーとは異なります。既定のイメージタグは `pdfscore_pipeline_gpu` です。別のタグを選ぶ場合は、各 `build`、`preflight`、`run`、`review` サブコマンドの前に同じ `--image YOUR_TAG` を指定します。

運用者が用意するモデルは不要です。#522 以降、検出処理は外部の OMR-DLN 小節検出器（`YOLOv8m_Measures.pt`）を使用しません。ダウンロードやマウントはしないでください。preflight を実行します。

```bash
python3 docker/distribution.py preflight
```

preflight は CUDA、ONNX CUDA プロバイダー、必須モデル、固定された HOMR ランタイムの来歴を確認します。必須モデルはすべてイメージ内蔵、または SHA-256 で検証される追跡対象の manifest です。モデルのバイト列を変更する場合は新しい manifest／バージョンが必要です。ビルドの成功だけでは GPU は確認されません。preflight はそれを確認しますが、楽譜の正確性は保証しません。

## PDF を処理する

```bash
python3 docker/distribution.py run /absolute/path/score.pdf --output /absolute/path/results
```

PDF と出力先の例をホスト上の絶対パスに置き換えてください。出力ディレクトリは書き込み可能で、配布ルートの外側にある必要があります。必要に応じて `--pages 1 2` を追加すると、1 から数える PDF ページを指定して処理できます。各ジョブには出力ルートの下に新しいディレクトリが作られます。その `final/` ディレクトリに番号付き PDF があり、`review/manual_correction_input.json` から補正アプリケーションを開きます。`result.json` にはステータス、警告、成果物のハッシュ、ソースの来歴が記録されます。レビューが必要なステータスは、生成結果に利用者の確認が必要であることを意味します。コマンドは `job_id` を含む JSON を表示します。以下の `JOB_ID` にはその値を使用してください。必要なら `ls -lt /absolute/path/results` で出力ルートを一覧表示し、`cat /absolute/path/results/JOB_ID/result.json` でジョブを確認できます。ジョブ作成前の失敗では `result.json` がない場合があります。端末のエラーを確認してください。結果を確認せずに最新ディレクトリが目的のジョブだと決めつけないでください。

出力ディレクトリには `/absolute/path/results` のように、配布物の checkout または展開先の外側を選んでください。ランチャーは、配布物のインベントリを後のレビューでも検証できるよう、配布物内の出力先をファイル作成や Docker 起動の前に拒否します。`DISTRIBUTION_PROVENANCE.json` のない開発 checkout では、`temp/results` のように Git の無視対象であるディレクトリも使用できます。ページを選択したレビューでは元の PDF ページ番号が表示されます。PDF 入力チェックに失敗した場合も、そのジョブの `result.json` にエラーの詳細が保存されます。

番号付き PDF は、レンダリング DPI や画像のリサイズに関係なく、トリミングや回転を含む元の PDF の表示ページサイズを保持します。古いレビューパッケージにはこのサイズ情報がない場合があります。その場合、利用可能なら画像の DPI を使用し、そうでなければ 300 DPI を仮定したことを警告します。そのようなパッケージで正確な用紙サイズを復元する必要がある場合は、元の PDF を再処理してください。

警告なしでジョブが成功した場合も、番号付き PDF を使う前にそのジョブのレビューアプリケーションを開き、[休符数の確認手順](#複数小節休符を確認して修正する)に従ってください。ジョブの成功は楽譜のレビュー完了を意味しません。

ローカルアダプターはレビュー用 handoff を移動後の保持済みソース manifest に結び付け、元の manifest のハッシュを記録します。保持したローカルジョブを開く際にも同じ準備が行われます。

出力ディレクトリ全体を保持してください。レビューパッケージ、ソース manifest、保持されたエンジン成果物は補正と検証可能な来歴を支えます。ランチャーは入力を `/input` に読み取り専用で、出力ルートを `/results` にマウントし、セッション間で安定したパスを使用します。サポート対象の dense ルートでは標準設定を使用し、評価／GT ファイルは不要です。

## レビューして修正済み PDF を生成する

```bash
python3 docker/distribution.py review --output /absolute/path/results \
  --handoff /absolute/path/results/JOB_ID/review/manual_correction_input.json
```

`JOB_ID` を表示された ID に置き換え、`run` と同じ出力ルートを使用します。同じ Linux ホストのブラウザーで `http://127.0.0.1:8010` を開きます。そのポートが使用中なら `--port 8011` を追加し、`http://127.0.0.1:8011` を開きます。アプリケーションは localhost のみにバインドし、Linux Docker のホストネットワークを使用します。ローカル利用を想定しています。言語切り替えで英語または日本語を選択できます。

Docker Desktop のホストネットワークは WSL や Windows と共有されないため、ランチャーは Docker Desktop を検出すると、コンテナー内の中継を通してホストの loopback のみにポートを公開します。WSL2 から実行し、Windows または WSL のブラウザーで同じ URL を開いてください。アプリケーションは引き続きコンテナーの loopback にバインドし、Host/Origin を検証します。この経路の確認範囲は NVIDIA GPU を備えた Windows + WSL2 のみで、主なインストール方法は引き続き Linux 用 Docker Engine です。

ページ画像と番号を確認します。小節線、小節、MMR の変更を保存で記録し、提示された楽章境界の根拠を確認してから適用前に確定します。アプリケーションは記録済みの編集と未保存の編集を別々に表示します。アプリケーションから修正済み PDF を生成し、完了を待って結果のリンクから開くかダウンロードします。適用前に未保存の編集とエラーを解消する必要があります。

### 複数小節休符を確認して修正する

自動番号付けは、使用前に確認する下書きとして扱ってください。**全ページの印刷されたすべての複数小節休符の数**を、アプリケーションの小節数と照合します。警告がない結果や高い認識信頼度は、数が正しいことを保証しません。検出漏れの休符は小節数 1 の通常小節として表示されるため、検出された休符や警告付きの結果だけを確認すると誤りを見逃します。休符付近の四角で囲まれた練習番号が休符数と誤認される場合もあります。

1. 上記の方法でジョブのレビューアプリケーションを開きます。**複数小節休符を確認**（**Check multi-measure rests**）の **全小節を確認**（**Inspect all measures**）を使用します。複数小節休符のタスクが選択され、数が 1 の小節を含む現在ページの全小節リストが開きます。すべてのページで確認を繰り返します。
2. 楽譜に印刷された元の休符の数字を読みます。オーバーレイが邪魔な場合は拡大するか非表示にします。キャンバスまたはリストで該当する物理的な小節を選択すると、ページ、段、小節、および元と現在の数が表示されます。表示される段／小節のインデックスは 1 から始まる位置であり、楽譜上の小節番号ではありません。
3. **複数小節休符の小節数を設定**（**Set rest measure count**）を選び、印刷された数を入力し、**修正を追加**（**Add change**）、**このページを保存**（**Save this page**）を選びます。1 と表示された検出漏れの休符にも、読み違えた休符にも同じ操作を使用します。通常の小節が誤って複数小節休符と扱われた場合は、代わりに **複数小節休符として扱わない**（**Do not treat as multi-measure rest**）を選びます。休符数の誤りを補うだけのために楽章をリセットしたり小節線を挿入したりしないでください。
4. 修正済み PDF を生成して開きます。修正した休符による増分、後続の段頭、次ページの先頭を、独立に数えた楽譜の番号と照合します。誤った 37 を印刷された 7 に変更すると、別途指定された番号リセットまで後続の番号が -30 ずれます。編集した枠だけの確認では下流への影響を見逃します。
5. ジョブ全体と保存済みの変更、適用試行を保持します。編集の保存や PDF 生成の成功は保存／適用を確認するものであり、音楽的な正しさを保証しません。休符を確実に読めない、特定できない、または修正できない場合は、その結果を未受け入れのままにし、ページ／位置と問題を報告して後で確認してください。

この手順は目視確認に依存し、すべての誤りが自動的に警告されることや休符を見落とさないことを保証しません。楽章リセットや小節線の誤りは別途確認・修正が必要です。それらの番号確認も通過してから修正済み出力を使用してください。

補正はレビューパッケージの `corrections/` ディレクトリに保持されます。各適用試行では、不変の入力コピーと使用した入力の来歴が `application_runs/` に保存されます。成功した修正済み PDF は各試行の `corrected/final/` ディレクトリにあります。失敗した試行の後も、以前に成功した出力は利用できます。サーバーは Ctrl+C で停止します。

元の PDF に注釈を付けたコピーで保存済みの補正状態を続けるには、**保存履歴・再開**（**Saved history / resume**）を開きます。未保存の編集を保存し、必要ならチェックポイントに名前を付け、**現在の修正を履歴に保存**（**Save checkpoint**）を選びます。保存済みチェックポイントを選択し、注釈付き PDF（最大 32 MB）を選んで、**別セッションで再開**（**Resume in new session**）を選びます。元のレビューは別に保持されます。ブラウザーの URL が再開セッションを識別し、サーバー再起動後にも開き直せます。保存時にもチェックポイントは自動的に保持されます。

チェックポイント導入前に作成されたジョブでは、**旧バージョンの保存済み入力**（**Saved inputs from earlier versions**）の項目を選び、**選択した保存入力を取り込む**（**Import selected saved inputs**）を選びます。アプリケーションはチェックポイントの作成前に元のソースと記録された補正の識別情報を検証します。利用できない項目には検証理由が表示されます。インポートは保存済み入力を検証するものであり、古い PDF が現在の成功結果であることを保証しません。再開セッションのチェックポイントを選んで別の注釈付きコピーを再開することもできます。それぞれの新しい URL は独立し、元のレビューの所有権の証拠を使用します。パネルの **PDF生成の履歴**（**PDF generation history**）には成功、失敗、中断した試行が記録され、後の成功によって以前の失敗が消えることはありません。

再開したキャンバスにはアップロードした注釈が表示されます。PDF 生成時には保持された認識成果物から番号を再計算し、五線の近くに一律 9 pt の段番号を追加します。注釈付き PDF の CropBox、元の注釈、背景は保持されます。安全な配置ができない場合はエラーを報告し、手書きを消去しません。レビューパッケージと、その `history/`、`resumed_sessions/`、保持済みソース成果物、生成された `.layer.json` ファイルをまとめて保持してください。履歴は外部の保持済み依存物を検証しますが、すべての認識成果物を含むポータブルなアーカイブは作成しません。

現在サポートされる再開入力は、元の全ページを順番どおりに含み、回転がゼロで、MediaBox と背景画像のバイト列が変わっておらず、ネイティブの Ink、Circle、Square、Stamp、FreeText または Highlight 注釈を使用するものです。CropBox の変更はサポートされます。

番号付き PDF を注釈のみ変更して MobileSheets から再エクスポートしたものも、それを生成したレビューから再開できます。その際、成功した PDF と `.layer.json` が利用可能な状態で保持されている必要があります。アプリケーションは保存済み結果に対してページ内容全体、管理対象の番号ストリーム、背景、レンダリングを検証し、以前の番号だけを除去して新しい手書きを保持します。内部 PDF オブジェクト番号は変わる場合があります。書き換えられた背景、変更されたページ内容、または欠落した来歴は拒否されます。

一部または並べ替えられたページ、フラット化／再エンコードされた背景、その他の対話型 PDF 図形には追加検証が必要です。元の背景とネイティブ注釈を持つコピーを書き出してください。アプリケーションは MSF ファイルをインポートせず、削除してよい手書き番号を推測しません。提供された 15 ページの MobileSheets 注釈のみの往復は確認済みですが、他のバージョン／エクスポート設定と物理印刷は未検証です。

## トラブルシューティングと来歴

- Git の失敗: Git の導入、リポジトリ URL、ネットワーク、アクセス権を確認して clone を再試行します。
- ビルド失敗: ビルド出力を保持し、ネットワーク接続とディスク空き容量を確認します。
- Docker の権限エラー: デーモン／ソケットへのアクセスと出力ファイルの所有権を確認します。
- 出力先が拒否された: 配布ルートの外にある絶対パスを選びます。
- ポートが使用中: 空いている `--port` を選び、localhost のそのポートを開きます。
- レビューの URL を開けない: Docker Desktop では、そのポートが Windows と WSL の両方で空いていることを確認します。ブラウザーとホストネットワークを共有しないその他の Docker 構成はサポート対象外です。
- GPU／プロバイダーが見つからない: Docker から GPU にアクセスできることを確認し、preflight を再実行します。ホストで GPU が検出されただけではコンテナー内の CUDA を利用できるとは限りません。
- モデルの欠落または破損: イメージを再ビルドするか、追跡対象の manifest の成果物を復元します。ハッシュが一致しない場合は別のモデルを選択せず失敗します。
- ランタイムの不一致: この配布物を別のイメージタグでビルドし、そのタグを使用します。
- レビュー／適用の失敗: ジョブディレクトリ全体を保持し、表示されたアプリケーションエラーを確認します。移動または部分コピーされたパッケージでは元の manifest／成果物が欠けている場合があります。
- 英語／日本語 UI: 両方の辞書はローカルアセットであり、翻訳サービスは不要です。

展開された配布物には、ソースコミット、dirty 状態、配布された全ファイルのハッシュを記録した `DISTRIBUTION_PROVENANCE.json` が含まれます。機械可読の選択一覧は [MINIMAL_MAINLINE_SURFACE.json](MINIMAL_MAINLINE_SURFACE.json) です。イメージラベル、preflight JSON、ジョブの `result.json`、補正で使用された入力の記録が、それ以外のランタイム／モデルと結果の識別情報を提供します。dirty な展開物は開発候補であり、不変のリリースではありません。

## ローカルストレージ容量

このリリースはローカルの Docker で実行されます。モデルアセット、一時／中間ファイル、保持するレビューパッケージ、最終 PDF に十分な空き容量を用意してください。PDF サイズ、ページ数、レンダリング画素数の preflight 制限は中間ストレージの上限を定めるものではありません。ジョブごとに 16 GiB のクォータを強制する機能、ストレージ増加に伴う自動キャンセル、受け付けたジョブが空き容量に収まる保証はありません。

OS がディスク満杯（`ENOSPC`）を報告すると、ジョブは `disk_capacity_exhausted` で失敗し、途中の作業／公開成果物の削除を試みます。クリーンアップ後にストレージが書き込み可能なら、アダプターは失敗した `result.json` を記録します。ファイルシステムが依然として満杯または書き込み不可の場合、この記録もできないことがあります。再試行前に空き容量を確保し、診断のため利用可能な失敗出力を保持してください。クォータとプロセスツリーの強制キャンセルは将来の公開サービス展開に先送りされています。

## 配布範囲

配布物は保守対象の dense PDF 設定を使用します。単独の番号付け CLI、任意の番号付けオーバーレイ、probe 診断画像、任意の wide candidate 分割は引き続き develop 専用ツールです。エンジンランタイムの来歴とデバッグテレメトリーは引き続き利用できます。

SR は専用バッチプロセスで生成されます。事前計算された SR の欠落や不正、破損した検出結果、必須 rescue seed の欠落があるとジョブは停止します。それらが黙って元解像度の画像や空の検出結果に置き換わることはありません。有効な空の予測は引き続きサポートされます。ページ単位の SR は明示的な develop 専用モードであり、配布物には含まれません。
