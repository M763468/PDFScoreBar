# Make-first 移行プレイブック（既存リポジトリ前提）

このドキュメントは「すでにリポジトリがあり、skillは使っているが
sh/シェル設定を作っていない」「Make
コマンドは2つだけある」状態から、**Make
をエージェントの安定APIにして、skills + artifacts
に寄せる**ための実務手順です。

## ゴール

-   エージェントは基本的に **Make ターゲット**を実行する（= 公開API）
-   出力は会話ではなく **artifacts/** にファイルとして残す
-   反復作業を検出して **Makeターゲット or skill**として追加できる
-   追加・変更は PR 単位で行い、破壊的操作は手動承認にする

------------------------------------------------------------------------

## 0. 前提（このプレイブックが想定する状況）

-   repo は既に存在
-   既存の skill 仕組みはあるが、実体はプロンプト寄りで sh がない
-   Make ターゲットが2つ程度ある
-   エージェント（codex/gemini CLI）が repo を直接参照できる

------------------------------------------------------------------------

## 1. 最小の土台を追加

### 1-1. artifacts/ を作る

-   `artifacts/` をリポジトリ直下に追加
-   `.gitignore` に `artifacts/*` を基本追加（ただし必要な成果物は docs/
    に移す）

例：

-   artifacts/test_results.txt
-   artifacts/repo_tree.txt
-   artifacts/lint_report.txt
-   artifacts/summary.json

### 1-2. agent.md を作る（ルールの単一ソース）

例（最低限）：

-   Make を最優先で探す・使う
-   stdout大量出力は禁止（ファイルに出す）
-   破壊的操作（削除・本番デプロイなど）は勝手にやらない
-   新規スキル/ターゲットは PR で追加
-   失敗時は artifacts にログを残して原因と次アクションを記録

### 1-3. docs/agent-skills/ を作る（参照ドキュメント置き場）

-   ここにこのバンドル内のドキュメントを置く想定

------------------------------------------------------------------------

## 2. Make を「公開API」にする

### 2-1. `make help` か `make list` を追加する

エージェントはまず一覧を見て判断したいので、ヘルプが重要です。

-   `make help` でターゲット説明一覧が出る
-   あるいは `make list` でも良い

### 2-2. 既存の2ターゲットを「artifact出力」に寄せる

もし既存ターゲットが stdout を大量に出す場合は、次の方針に統一します。

-   コマンド出力 → `artifacts/<name>.*` に保存
-   成功/失敗が exit code で判定できるようにする
-   可能なら機械可読（JSON）も併記

------------------------------------------------------------------------

## 3. "基本4技能" を Make ターゲットとして足す

最初に追加すると運用が安定する定番4つ：

1)  repo-tree（構造把握）
2)  tests（テスト実行）
3)  lint（静的解析）
4)  build（ビルド）

例（内容はリポジトリの実態に合わせて差し替え）：

-   repo-tree: `tree -L 3 > artifacts/repo_tree.txt`
-   tests: `pytest -q > artifacts/test_results.txt`
-   lint: `eslint . --fix > artifacts/lint_report.txt`
-   build: `npm run build > artifacts/build_log.txt`

重要：コマンドは1つでもOK。**artifactに固定**するのが価値。

------------------------------------------------------------------------

## 4. skills/ は「説明」と「補助実装」に寄せる

Make を主入口にする場合、skills は以下の2用途で残すのが安定します。

### 4-1. "説明スキル" としての SKILL.md

-   いつ使うか（判断基準）
-   入力（引数、前提）
-   出力（artifactsのパス）
-   失敗したときの次の観察ポイント

### 4-2. Make から呼ぶ run.sh（必要なときだけ）

-   Makefile 内で `./skills/<name>/run.sh` を呼ぶ
-   `set -euo pipefail`
-   出力は artifacts に固定
-   外部依存（node/python等）は明示

------------------------------------------------------------------------

## 5. 自己進化（増やす基準と手順）

### 5-1. 追加トリガー（増やす基準）

次のいずれかを満たしたら "skill候補"：

-   同じコマンド列を 2〜3回繰り返した
-   実行手順がブレる（人/エージェントで違う）
-   ログが長く、コンテキストを圧迫する
-   成功/失敗の判定が曖昧
-   依存関係（事前にやるべきこと）が発生している

### 5-2. 追加物（必須成果物）

-   Makeターゲット追加（第一候補）
-   もしくは `skills/<name>/` の追加
-   `docs/agent-skills/skill-index.md` 更新
-   `agent.md`
    に「このスキルは何のために追加したか」を短く追記（運用の理由が残る）

### 5-3. 安全策

-   新規追加は PR で（main直コミット禁止）
-   破壊的操作は Make/skill に入れない（手動承認）
-   secrets を出力しない（ログ/ファイルに書かない）

------------------------------------------------------------------------

## 6. 受け入れ基準（Done の定義）

エージェントが次を満たせば移行完了：

-   `make help` で実行可能タスクが一覧化される
-   `make repo-tree/tests/lint/build` が動き、`artifacts/` に結果が残る
-   エージェントが「まず Make を使う」動きになる
-   反復作業が発生したとき、新ターゲット/スキルとして提案・追加できる
