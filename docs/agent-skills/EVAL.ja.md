タスクの成果を改善することを目的としたリポジトリの Skill を追加したり大きく変更したりするときは、この小さく繰り返し実行できる手順を使います。これは手作業による比較の手順です。通常のコード変更のたびに実行しないでください。

## ケース

| 機能 | 代表的なタスク | 否定の対照 |
| --- | --- | --- |
| PR へのフィードバック（`pr-refinement`） | 具体的な変更要求が1つと、あいまいな提案が1つある PR について、文脈を取得し、具体的な要求だけを実装する。 | PR の説明を求められた場合に、ファイルを変更したりコメントを投稿したりせずに要約する。 |
| Issue の事後分析（`issue-post-mortem`） | 完了した作業を、固定した Issue の受入条件と比較し、不足を報告する。 | 実装のタスクを与えられた場合に、事後分析のワークフローを使わない。 |
| モジュール横断のナビゲーション（`graphify`） | 難しい呼び出し経路の質問に、既存のグラフを使って答え、その結果をソースで確認する。 | 単一ファイルの通常の変更では、グラフへの問い合わせや更新をせず、ソースから答える。 |
| OMR の画像レビュー（`visual-diff-viewer`） | 固定したデバッグ画像のディレクトリから最近の画像を特定し、指定された見た目の欠陥がないか確認する。 | 画像の根拠を求められていない、テキストだけのコードレビューでは、画像を走査したりコピーしたりしない。 |

## モードと採点

各ケースについて、同じプロンプト、リポジトリのスナップショット、利用できるツールを使って、3回実行します。

1. Skill を選ばない。
2. Skill を明示的に選び、その `SKILL.md` を与える。
3. Skill をインストールし、暗黙の選択のためにその説明だけを利用できる状態にする。

また、Skill をインストールした状態で、記載した否定の対照も実行します。タスクの成否、不要なコマンドやファイルの変更、検証の網羅、利用できる場合はターン数やトークン数、外部への書き込みやサンドボックスの境界のエラーを記録します。実行を成功と数えるのは、タスクで定めた成果を満たし、かつリポジトリの方針に違反しない場合だけです。結果を短い表で比較し、プロンプト、commit、モデルとランタイム、結果のメモを、関連する Skill の変更や PR とともに残します。成功率を改善しない、または重大なエラーを減らさない Skill は、範囲を絞るか削除すべきです。
