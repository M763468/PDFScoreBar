この文書は、`AGENTS.md` を中心とした、リポジトリの軽量なワークフローを説明します。第二の指示体系ではなく、特定のモデル、Skill、オーケストレーションの層を必要としません。

## 情報の正本

作業中は次の順に従います。

1. 最新の利用者の指示
2. 作業が Issue/PR に基づく場合は、現在の Issue/PR
3. 現在のソース、テスト、Git の状態
4. リポジトリの正規の文書
5. 関連する過去の Issue/PR と履歴の記録

古いセッションの状態、ブランチの状態、コンテナの状態、古い「次のステップ」を、再確認せずに復元しないでください。

## 通常の開発の流れ

1. 具体的なタスクと範囲を特定します。
2. そのタスクに必要なソース、文書、履歴だけを確認します。
3. 通常の作業では `develop` からブランチを作ります。`docs/BRANCH_POLICY.md` を参照してください。
4. タスクを満たす、最小限で一貫した変更を実装します。
5. `docs/dev/VALIDATION_POLICY.md` から検証を選びます。
6. 差分を確認し、範囲の逸脱や、意図しない config・依存関係・評価の変更がないか確かめます。
7. 依頼されている場合、またはすでに認められている場合は、正しいベースへ push して PR を作り、`.github/pull_request_template.md` を使います。

目標・範囲・受入条件を残しておくと役立つ作業には Issue を勧めますが、リポジトリの保守や、その他の明示的に依頼されたタスクのために、ワークフローを満たすだけの目的で Issue を作る必要はありません。

## Skill

Skill は任意で使う高速化の手段です。通常のリポジトリの操作は、限定されたプロジェクト固有の Skill の方が適している場合を除き、エージェント自身のリポジトリ/GitHub の機能を使います。

現在のプロジェクト固有の用途には次があります。

- `issue-post-mortem`: 完了した調査を、その記録が実際に必要な場合に、長く残る証拠へまとめます。
- `pr-refinement`: 特定の PR について、ページ分割されたインラインのレビューコメントを取得し、対応すべきフィードバックを分類します。
- `graphify`: 難しいモジュール横断の依存関係や呼び出し経路の質問について、既存のグラフに問い合わせます。
- `visual-diff-viewer`: 画像の比較が役立つ場合に、関連する OMR の画像を集めます。

通常の状況報告、Issue/PR の読み取り、PR の作成、文書の更新、テストの生成、依存関係の確認、差分の説明、一般的なデバッグには、エージェント自身の機能を使います。専用の Skill は、その説明が明確なプロジェクト固有の必要性に合う場合にだけ選びます。

## Graphify

Graphify は任意です。局所的な質問には、ソースとテストを直接確認する方を優先します。モジュール横断のアーキテクチャや呼び出し経路の質問で役立つ場合に既存のグラフを使い、重要な結論は現在のソースで確認します。`docs/ai-workflow/GRAPHIFY.md` を参照してください。

コードベースについて質問されたというだけの理由で、グラフをインストール、再構築、更新、意味情報で拡充しないでください。

## 他のモデルへの相談

Codex/Gemini への相談は、既定のワークフローの一部ではありません。明示的に依頼された場合、または難しいタスクで独立したセカンドオピニオンが実質的に役立つ場合にだけ、別のモデルを使います。通常の作業で、役割の宣言、単一の書き手の手続き、相談の成果物、セッション終了時の教訓、リポジトリのログを要求しないでください。

## GitHub への書き込み

Issue、コメント、レビュー、ブランチ、PR の作成・編集は、タスクがそれらの操作を依頼または許可している場合に適切です。読み取りだけの質問で、自動的に GitHub へ書き込むべきではありません。

## 長く残す実験の履歴

大規模な性能・評価の調査では、採用・不採用の判断と再現可能な来歴を、関連する Issue/PR またはリポジトリの履歴の記録に残します。チャットの記録全体や、一時的な作業キューは残しません。

実際の運用ルールはルートの `AGENTS.md` を参照してください。
