## 概要
`src/common/barline_evaluation.py` モジュールは、予測したバーラインのボックスを正解データ（GT）と比較するための共有マッチャーを提供します。HOMR評価スクリプト（`src/homr_eval_scripts/`）と `tools/` 配下の評価・診断ツールがこれを使用します。マッチャーは細いバーラインの形状を正規化し、IoUに基づく貪欲マッチングを行い、惜しい検出（near-miss）を分類します。これにより、下流のレポートが検出の昇格・降格を一貫して扱えます。これは評価の契約であり、本番パイプラインがどのバーラインを出力するかを決めるものではありません。

## 形状の正規化
- 予測とGTの各ボックスは、IoUを測る前に `expand_barline_box` でパディングされます。
- 既定パラメータ（`src/common/barline_geometry.py` で定義され、マッチャーとその呼び出し側がimport）:
  - `BARLINE_DEFAULT_MIN_WIDTH = 12`
  - `BARLINE_X_MARGIN = 3`
  - `BARLINE_Y_MARGIN = 3`
- パディングはボックスの中心を固定したまま最小幅を保証し、画像サイズが与えられた場合はその範囲内にクランプします。これにより、わずかな幅の違いでIoUがゼロになる問題を緩和します。

## 貪欲マッチング
1. パディング後のボックスと設定済みのIoU閾値（評価器では通常 `iou_threshold` = 0.5）を使い、密なIoU行列を作ります。
2. IoUの要素が残っている間、スコアが最も高いペアを貪欲に選び、その行と列を取り除きます。
3. 確定マッチ（hard match）を `(prediction_index, ground_truth_index, iou)` のタプルとして記録します。

行列の作成中、マッチャーは各予測について2種類の「最良」参照も記録します。
- **Strong best** – 縦方向の重なりが `BARLINE_VERTICAL_OVERLAP_THRESHOLD`（0.6）以上であることを要求します。
- **Fallback best** – 重なりに関係なくIoUが最大のもの。同点の場合は重なり、次にX距離で決めます。
これらの記録は、後述のソフトマッチ分類に使われます。

### 正規の中心アンカー（Canonical Center Anchor）

正規の strong pair 判定では、`center_anchor` は縦方向の重なりが `0.5` 以上で、
中心のX距離が `0.5 * unit_size` 以下であることを要求します。`unit_size` は、
比較するボックスとまったく同じ座標系で測ったページの五線間隔です。正規の利用側は
これを `barline_staff_units.v1` ページmanifestで渡します。このmanifestは座標系の
寸法と元データの来歴も記録します。明示的なピクセル閾値を渡すのは、過去結果を再現する
レガシーモードに限られます。

以下の用語は別々の契約を表しており、混同してはいけません。

- **ペアの適格性（pair eligibility）** は上記の幾何条件です。同じGTに対して
  複数の候補が適格になることがあります。
- **候補ごとの学習ラベル** は、引き続きデータセット作成側の `any pair`
  ターゲットです。適格なGTが1つでもあれば、その候補は正例になります。作成側は
  意図的に、所有者（owner）方式や1対1方式へは変更していません。
- **貪欲な評価割り当て** は各GTを最大1回だけ消費し、確定マッチと、
  duplicate/repeat のソフト分類を記録します。この割り当ては、候補ごとの
  分類器の学習ラベルに代わるものではありません。

## 重複（Duplicate）と反復記号様（Repeat）の分類
貪欲なペアリングの後、マッチしなかった予測を再確認します。
- **重複（`reason="duplicate"`）** になる条件:
  - fallback best とのIoUが `BARLINE_DUPLICATE_IOU_THRESHOLD`（0.3）以上、かつ
  - X距離が `BARLINE_DUPLICATE_X_TOLERANCE` 以下（12 px。このソフト分類は `unit_size` 基準へ移行していません）。
- **反復記号様（`reason="repeat_like"`）** になる条件:
  - 縦方向の重なりが `BARLINE_REPEAT_OVERLAP_THRESHOLD`（0.8）以上、
  - X距離が重複の許容値と `BARLINE_REPEAT_X_TOLERANCE`（40 px）の間。

どちらの規則にも当てはまらない予測は、確定の誤検出（hard false positive）として扱います。

### 動的な正規化（解像度非依存）
従来の閾値はピクセル（px）で定義されていますが、新しい距離の閾値は **unit_size（五線間隔）** を基本単位にしています。小節番号付けの論理層（`src/measure_numbering/numbering.py` の `MeasureNumberer`）は次を使います。
- **重複除去の閾値**: `1.2 * unit_size`
- **暗黙の開始とみなす閾値**: `4.0 * unit_size`
これにより、論理層は楽譜の解像度（例: 300dpi と 600dpi）が違っても一貫して動作します。

上記の中心アンカー契約は、意図的に strong `center_anchor` の判定だけに限定しています。
従来のIoUパディングや、duplicate/repeat のソフト分類のピクセル閾値を
解像度非依存にするものではありません。

正規のページmanifestは `data/evaluation2/staff_units.json` で管理しています。
その `source_sha256` 値は、外部の五線マスクのスナップショットに対する完全性の境界を
定めます。元データを実体化した場合、利用側はそのハッシュを検証できます。正規の
中心アンカーの利用側はすべて、マッチングの前に manifest の寸法が実際の入力画像の
寸法と一致することも確認します。

## 左余白の除外規則
`apply_left_margin_exclusion` はマッチングの後に実行され、特定の検出を誤検出へ分類し直します。HOMR評価器（`src/homr_eval_scripts/homr_evaluator.py`）は現在このガードを無効にしている（`LEFT_MARGIN_FORCE_FP_GT_INDICES = set()`）ため、既定では降格されるマッチはありません。再び有効にした場合、このセットに含まれるGTインデックスのうち、予測の幅が `LEFT_MARGIN_FORCE_FP_MAX_WIDTH`（2 px）以下のものとマッチしたものは誤検出に戻されます。これは、意図的に無視する左余白の縦線を抑えるためです。

`margin_x` が与えられた場合（現在は未使用）、このヘルパーは、中心が余白内にある予測を、マッチしたGTの中心とあわせて降格させます。これにより、他の楽譜で左余白の抑制を設定できます。

## 出力の契約
マッチャーは次を含む `BarlineMatchResult` を返します。
- `matches`: 確定した正検出（TP）のペア
- `false_positive_indices`: duplicate/repeat の除外後もマッチしなかった予測
- `false_negative_indices`: マッチしなかった正解ボックス
- `soft_matches`: GTインデックスとの関連は保つがTPとしては数えない、duplicate/repeat様の記録。可視化のオーバーレイでは通常「OK」と表示されます。

## オーバーレイ可視化
評価スクリプト（例: `src/homr_eval_scripts/homr_evaluator.py` と `src/homr_eval_scripts/core/reporting.py`）がオーバーレイ画像を生成するとき、検出の質を次の表示で表します。

-   **緑のボックス（`TP#{index}`）**: **正検出（True Positive）**。検出が正解のバーラインと正しくマッチしました。
-   **赤のボックス（`FP#{index}`）**: **誤検出（False Positive）**。検出はどの正解バーラインともマッチせず、ソフトマッチにも分類されませんでした。
-   **オレンジのボックス（`OK#{index}:dup` または `OK#{index}:rep`）**: **ソフトマッチ**。もっともらしいが正しくない検出で、最終的な TP/FP/FN の指標からは明示的に除外されます。
    -   `OK...:dup`: より良い予測ですでにマッチした正解バーラインと重なる、**重複**検出。
    -   `OK...:rep`: **反復記号様**の検出。反復記号や太い符尾など、見た目がバーラインに似ているもの。

## 細いバーラインの回収ヒューリスティック（過去の記録、2025-10）
共有の `src/common/thin_barline_finder.py` ヘルパーは、主要モデルが見逃した細い縦線で検出器の出力を補います。HOMRランタイムの predictor（`src/homr_runtime/predictor.py`）とHOMR評価器が使用します。2025年10月の更新で、次が導入されました。

- **縦方向の分割への対応**: 同じX座標を共有する候補でも、縦方向の中心が五線の高さ以上離れていれば共存できるようになりました。これにより、段（システム）の間で誤って上書きすることを防ぎます。
- **隣接条件の緩和**: すぐ隣の 3 px がやや暗くても、より広い 6 px の範囲で背景の明るさに戻れば、そのバーラインを残します。これにより、符幹のすぐ横にある反復記号の縦線を捉えます。
- **標準偏差のフォールバック**: 幅 1〜4 px の縦線は、両隣が背景と読み取れる場合、より大きな輝度のばらつき（≤80）を許容します。これは GT インデックス {97,147} で見られた黒白混在のペアに対応するためです。
- **片側ガード**（2025-10-17）: 片側の隣接部分が確実に背景で、反対側が符幹や強弱記号の集まりで暗い場合、暗い範囲が完全に塗りつぶされていなければ（`single_side_dark_ratio ≤ 0.6`）検出を残します。この上書きが働くときは、符頭として棄却するには両隣が密であることを要求するようになりました。
- **縦方向の隙間の閉鎖**（2025-10-17）: ランレングス解析の前に、高さ 3 px のモルフォロジー閉処理で加線や休符による短い隙間をつなぎます。これにより、GT 137 のような分割された縦線を回収できます。

当時、これらのヒューリスティックにより、`page_003` で共有されていた見逃し（false negative）は6件から4件に減り、誤検出の増加も抑えられました（homr run `20251015T010556JST_fn_vertical_split_v5`: TP=148 FP=8 FN=4、precision 0.949 / recall 0.974）。同じロジックは以前のOEMER評価器にも適用されました（`20251015T010745JST_baseline`: TP=152 FP=6 FN=0）。OEMER評価器は現在の保守対象のソースツリーには含まれていません。これらの数値はその実行時点の評価記録であり、現在の本番経路を保証するものではありません。

評価器はこれらの結果を、評価器の実行ディレクトリ（以前は `logs/<pipeline>/<timestamp>/`）に `metrics.json`、`metrics.csv`、オーバーレイ画像、人が読むための `compare.md` として保存します。
