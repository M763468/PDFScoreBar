# エンジンの信頼できないPDFに対する安全性契約

翻訳元: same PR / SHA-256 `4a9e69a6d99a57fdb54dfb3fac63e03a93191dd5829d801ed3314761b018bcc6`。状態: `reviewed`。全文の意味・制約・例外を原文と照合し、日本語の可読性も確認済み。

本書は、バージョン付きエンジン境界を通して1つの信頼できないPDFを処理するための、規範となるIssue #338の安全性契約である。

初期のローカルDocker配布（#410）では、この契約が強制するのはPDF入力の事前検証上限だけである。ジョブごとの実行時ディスククォータは提供せず、ストレージ使用量の増加によって実行中のジョブを強制停止することもない。強制的なストレージ分離とプロセスツリーのキャンセルは、将来の公開サービスへのデプロイまで保留とする。

この契約は、次の契約を基盤として定義する。

- v1のrequest/result/error形式を定める[エンジンジョブ契約](ENGINE_JOB_CONTRACT.ja.md)
- 実行期限、キャンセル、公開、クリーンアップの意味を定める[ライフサイクル契約](ENGINE_JOB_LIFECYCLE.ja.md)

現在の設定起点の本番パイプラインは、運用者・信頼された入力向けのワークフローのままとする。Issue #338は、任意のリポジトリパスや現在のYAML設定を、黙って公開アップロード APIへ変えるものではない。

再利用可能な実装は `src/pipeline/engine_input_safety.py` にある。

## 1. セキュリティ境界

匿名またはその他の信頼できない呼び出し側が、1つのエンジンリクエストを無制限の処理や任意のホストファイルシステム・ネットワークへのアクセスへ転用できてはならない。

将来の信頼できない入力を受ける1ジョブアダプターでは、次を行う。

1. 呼び出し側がPDFのバイト列、またはステージング済みのエンジン参照を渡す。
2. アダプターがワーカー所有の入力ルート以下へ入力をステージングする。
3. エンジンがパス、バイト数、PDF、ページ、予測レンダリング上限を事前に検証する。
4. 拒否した入力については、可能な限りページレンダリング・モデル推論へ進む前に、構造化されたv1 `EngineError` を返す。
5. 受理した処理を、ワーカー・コンテナのリソース境界内で実行する。
6. 非失敗の終端 `JobResult` が提示した成果物だけを公開する。

認証、アカウント、課金、全体のレート制限、IPレピュテーション、キューの公平性、ジョブ間スケジューリングは、引き続きサービス・コントロールプレーンの関心事である。それらは、ここで定めるジョブごとの上限の代わりにはならない。

## 2. 現在のランタイム監査

現在のリポジトリには有用な安全性の部品があるが、設定起点の経路は任意の公開アップロードを受け付けるようには設計されていない。

| 領域 | 現在の挙動 | Issue #338からの帰結 |
| --- | --- | --- |
| PDF バイトの読み込み | `PipelineOrchestrator._run_pdf_to_images()` はPyMuPDFを開く前に `Path.read_bytes()` を呼ぶ | 信頼できない入力向けアダプターは、現在の無制限な読み込み方式の前にバイト上限を強制しなければならない |
| PDF解析 | PyMuPDFは入力元の全バイトを開き、`page_count` を公開する | パーサーエラー・暗号化には、決定的で公開用に安全なマッピングが必要 |
| レンダリング | `render_pdf_to_memory()` は `page.get_pixmap()` を呼び、レンダリング済みページをリストへ蓄積する | レンダリング前に予測寸法・ページ別ピクセル数・総ピクセル数を制限しなければならない |
| ページ選択 | 既存ヘルパーは選択ページのインデックスを検証する | 信頼できない入力の実行には、さらに文書ページ数・選択ページ数の上限が必要 |
| 入力パス | 設定は運用者指定のパスを受け付ける | 公開ジョブはワーカー所有の入力ルート内でのみ解決し、トラバーサル・URL形式の参照を拒否しなければならない |
| シンボリックリンク | 一般的な公開入力のシンボリックリンク方針がない | 信頼できない入力では、既定でシンボリックリンクをたどらない |
| 出力名 | v1は呼び出し側の `output_name` を公開する | ファイル名のステムだけであり、パスではない |
| 成果物パス | v1成果物の `relative_path` は、すでに絶対パスと `..` トラバーサルを拒否する | この既存契約を維持する |
| 子プロセス | 高負荷ステージは、すでに複数の経路でプロセス境界を使う | #337で規定する終了処理の仕様を満たすには、引き続きワーカー・プロセスグループの統合が必要 |
| 実行時ダウンロード | 本番モデル・ランタイム資産はビルド・準備時に明示的に実体化され、ランタイムリゾルバーがローカル資産を検証する | 通常のジョブ実行はオフラインを維持し、必要なローカル資産が利用できなければ失敗しなければならない |
| ログ | 現在の内部パイプラインログは、完全なローカルパスや子プロセス出力を含み得る | `pipeline.log` は診断用であり、公開の呼び出し側応答ではない |
| クリーンアップ・公開 | #337は試行クリーンアップを定義し、内部パスの存在は公開ではないとする | 上限・入力による拒否は試行の失敗であり、不完全な最終/レビュー成果物を公開してはならない |

直接のPDF レンダラーは入力元のハッシュも計算し、来歴を記録する。これは有用な内部証跡だが、将来の公開結果では、内部の絶対パスを公開メタデータへコピーしてはならない。

## 3. ジョブごとの既定方針

`JobSafetyPolicy` は具体的な既定値を提供し、ワーカー・サービスアダプターがデプロイ先に合わせてより厳しい値を選べるようにする。

| 制限 | 既定値 |
| --- | ---: |
| PDF バイト | 256 MiB |
| 文書ページ数 | 500 |
| 選択ページ数・生の要求ページ指定数 | 200 |
| ページごとのレンダリング幅 | 12,000 px |
| ページごとのレンダリング高さ | 12,000 px |
| ページごとのレンダリングピクセル数 | 64,000,000 |
| 選択ページの総レンダリングピクセル数 | 1,000,000,000 |
| 入力のシンボリックリンクトラバーサル | 拒否 |
| ワーカー所有の入力ルート | 必須 |

これらは事前検証の拒否上限であり、上限未満のすべてのジョブがあらゆるマシンで処理可能だという主張ではない。デプロイ先はv1通信スキーマを変えずに値を引き下げてよい。引き上げは運用・セキュリティ上の判断であり、後述する将来の公開サービスワーカー要件を取り除くものではない。

ページ・ピクセル制限は、`get_pixmap()` の前に、PyMuPDFのページ形状と実際に要求されたレンダリング DPIから計算する。出力の増幅を制限するが、極端な構造を持つPDFの解析・レンダリングの処理負荷が軽いことまでは保証できない。

## 4. PDF 事前検証契約

`validate_local_pdf()` が、再利用可能な事前検証を行う。

### 4.1 パス・参照チェック

信頼できない `local_path` リクエストでは、次を適用する。

- `http:`、`https:`、`file:` などのURI スキームを持つURL形式の参照を拒否する。
- 制御文字と明示的な `..` パス要素を拒否する。
- 解決後のファイルは、ワーカー所有の `allowed_root` 内に収まらなければならない。
- 既定でシンボリックリンク要素を拒否する。
- 最終的に開いた対象は通常ファイルでなければならない。
- 利用可能な環境では、ファイル 記述子単位の通常ファイルチェックより前に非ブロッキングで開く。これにより、FIFOなどの特殊ファイルが相手待ちで事前検証を停止させることを防ぐ。
- アダプターは検証開始前に、信頼できない呼び出し側がステージング済み入力ルートを変更できないようにすべきである。

実装は、利用可能なら最終ファイルに `O_NOFOLLOW` も使う。別の主体が親ディレクトリを並行して変更できる場合、ファイルシステム検証だけではすべてのtime-of-check/time-of-use raceを排除できない。そのため、ワーカー所有で攻撃者が書き込めないステージングルートも契約に含める。

`engine_ref` はエンジン所有の不透明な識別子である。ストレージへの解決はアダプターの責務だが、解決された対象も、レンダリング前に同じ上限付きPDF検証経路を通らなければならない。

### 4.2 上限付きバイト読み込み

入力を通常ファイルとして開き、`max_pdf_bytes` まで段階的に読み込む。同じ読み込み中にSHA-256を計算する。設定上限を超えるサイズを観測した場合は、PyMuPDFの解析前にジョブを拒否する。ステージング済み入力を開く・検査する・読む際に想定されるファイルシステムの失敗は、生の `OSError` 例外を外へ出さず、安定した `input_pdf_unavailable` エラーへ正規化する。

信頼できない入力向けの上限付き事前検証は、現在の「検証前に `Path.read_bytes()`」という方式を意図的に避ける。

### 4.3 PDFの妥当性と暗号化

次は、決定的で再試行不能な入力失敗となる。

- 読み取り不能・不正・PDF以外の内容
- 0ページのPDF
- パスワード保護・暗号化されたPDF

Issue #338はパスワード処理を追加せず、呼び出し側入力の復号も試みない。将来暗号化入力に対応するには、別途明示的な認証情報・シークレット取り扱い契約が必要となる。

### 4.4 ページとレンダリング計画の制限

ページ内容をレンダリングする前に、事前検証では次を確認する。

- 文書の総ページ数
- 重複除去前の生の要求ページ指定数
- 選択ページ数
- 選択ページインデックス
- 要求DPIでの予測幅・高さ
- 各選択ページのピクセル数
- 選択ページ集合全体の総予測ピクセル数

検証済みメタデータには、入力元のベース名、SHA-256、バイトサイズ、ページ数、選択ページ、レンダリング DPI、寸法・ピクセル数、総レンダリングピクセル数を含める。ワーカーのローカル絶対パスは意図的に省く。

PDF内に埋め込まれたオブジェクトや画像の寸法だけでは、十分なセキュリティ指標とはみなさない。ベクターデータ、圧縮ストリーム、その他のPDF構造によっても、依然として高い処理負荷が生じ得るためである。レンダリング出力の上限とワーカーの強制制限の組み合わせが、セキュリティ境界となる。

## 5. 出力名とパス構築

v1の `config_overrides.output_name` は、呼び出し側に見えるファイル名のステムだけを表す。

空であってはならず、次を含んではならない。

- `/` または `\\`
- 値全体が `.` または `..`
- ASCII制御文字
- 200 UTF-8 バイトを超える値

ディレクトリはエンジン・アダプターが選ぶ。呼び出し側は `output_name` を使って絶対パス、親ディレクトリ、モデルパス、実行ルート、一時ルート、その他の内部の場所を選べない。

既存のv1成果物記述子は、別の包含規則を維持する。`relative_path` 成果物は絶対パスにできず、`..` を含められない。

## 6. 構造化された拒否カテゴリ

事前検証失敗は、既存のv1 `EngineError` エンベロープへマッピングする。

| 条件 | カテゴリ | コード | 再試行可否 |
| --- | --- | --- | --- |
| 不正・読み取り不能PDF | `input` | `input_pdf_invalid` | false |
| 暗号化・パスワード付きPDF | `input` | `input_pdf_encrypted` | false |
| 入力の欠落・通常ファイル以外 | `input` | `input_pdf_unavailable` | false |
| URL・トラバーサル・シンボリックリンク・ルート外の入力 | `input` | `input_reference_not_allowed` | false |
| 無効なリクエストページリスト | `invalid_request` | `request_pages_invalid` / `request_page_out_of_range` | false |
| 安全でない出力ステム | `invalid_request` | `output_name_invalid` | false |
| 入力バイトが方針を超過 | `resource` | `input_pdf_bytes_limit_exceeded` | false |
| 文書・選択ページ数が方針を超過 | `resource` | `input_pdf_page_limit_exceeded` / `input_pdf_selected_pages_limit_exceeded` | false |
| レンダリング寸法が方針を超過 | `resource` | `input_pdf_render_dimension_limit_exceeded` | false |
| ページピクセル数が方針を超過 | `resource` | `input_pdf_render_pixels_limit_exceeded` | false |
| 総レンダリングピクセル数が方針を超過 | `resource` | `input_pdf_total_render_pixels_limit_exceeded` | false |
| 実行中にOSが容量不足（`ENOSPC`）を報告 | `resource` | `disk_capacity_exhausted` | true |

設定上限による拒否は、エンジンの非成功結果となる。変更なしで自動再試行してはならず、不完全な最終/レビュー成果物を公開してはならない。

## 7. 公開用に安全な情報と診断情報

`InputSafetyError.to_engine_error()` が、事前検証失敗をv1エンベロープへマッピングする。

公開応答に含めてよいもの:

- 安定したカテゴリ/コード
- 範囲を限定した `public_message`
- ユーザーが対処できるか・再試行可能かの情報
- 結果契約向けに意図的に選択した検証済みメタデータ

公開応答に含めてはならないもの:

- ホスト・コンテナの絶対パス
- 意図的に公開する呼び出し側参照またはサニタイズ済みベース名を超える、任意の呼び出し側ファイル名
- パーサーのスタックトレース
- 子プロセスのコマンドライン・環境
- モデル・キャッシュの場所
- 内部の実行・一時ディレクトリ名
- 生の `pipeline.log`

正確なパーサー例外、内部パス、観測した制限値、ステージ名、スタックトレースは、信頼された診断・`debug_context` に存在してよい。`EngineError.to_dict()` は、引き続き既定で `debug_context` を省く。

## 8. ランタイムのネットワークとモデル資産

通常の1ジョブ実行はオフライン契約である。

正規のイメージ・ビルド経路は、すでに管理対象のHOMR、過去のStage-E HOMR、Real-ESRGAN、本番 CNN資産をイメージ構築・準備時に実体化する。ランタイムリゾルバーは実体化済みのローカル資産を検証し、必須資産がなければ失敗する。

`src.common.model_artifacts materialize` は明示的な運用者・ビルドの操作であり、ネットワークを使ってよい。ジョブエグゼキューターは、ジョブを成功させるためにこの操作、HOMR初期化時ダウンロード、任意のURL、同等のダウンロードヘルパーを呼び出してはならない。

サービスワーカーは、既定で外向きネットワークを無効にして動作すべきである。サードパーティ製の依存ライブラリが予期せずダウンロードを試みた場合は、PDFジョブにネットワークアクセスを許可するのではなく、その試行を失敗させ、`dependency` または `internal` の失敗として扱うべきである。

外部から供給するOMR/MMR/モデル資産も同様に、信頼できないジョブを受け付ける前にステージング・検証しなければならない。

## 9. 将来の公開サービスワーカー・コンテナ要件

PythonレベルのPDF検証は必要だが、十分ではない。解析自体や受理したPDF内容が予期しないCPU/RAMを消費し得るため、ネイティブ PDF/CUDA/ランタイムコードも信頼できない入力の境界の一部として扱わなければならない。

任意のPDFを受け付けるワーカーは、検証用ヘルパー単体ではなく、その外側のワーカー・コンテナ環境で次を提供しなければならない。

- 使い捨ての1ジョブ試行ワークスペース
- ワーカー所有のルート以下へステージングし、実行中は読み取り専用・攻撃者による書き込み不可とした入力
- 実用上可能ならrootユーザー以外で動作するプロセス
- Docker ソケットや無関係なホストファイルシステムのマウントを持たないこと
- 読み取り専用のランタイム・モデル資産
- CPUとRAMの上限
- デプロイ先に適したGPU配置・VRAM影響の上限
- #337の協調的チェックポイントに加えた、強制的な試行期限
- 一時データ/中間データ/最終 ステージング用の書き込み可能なファイルシステム・ボリュームの上限
- 停止しない子プロセスに対するプロセスグループ・コンテナ終了
- 通常ジョブの外向きネットワーク無効化
- 強制終了後の試行ワークスペースの隔離・削除

初期のローカルDocker配布は、これらのサービス分離制御を実装しない。`JobSafetyPolicy` が持つのは入力の事前検証上限だけであり、`resource_budget()` はそれらの上限を報告するもので、実行時のCPU/RAM/ディスクを保証しない。以前の `max_attempt_disk_bytes` 方針フィールド、`enforce_attempt_disk_budget()` フック、ポーリング監視は削除された。これらは使用量を検知できても、内部を制御できないランナーや子プロセスが書き込みを続ける間、上限を強制できなかったためである。Python呼び出し側はその方針引数を削除しなければならず、互換性用の引数を黙って無視することはない。v1のrequest/result/error通信スキーマは変更しない。

ローカル運用者は、モデル資産、一時ファイル、保持するレビューパッケージ、最終出力に十分な空き容量を用意しなければならない。検証した入力サイズ・ページ数・ピクセル数は、中間ストレージ総量を制限せず、受理したジョブが利用可能なディスクに収まる保証もない。OSの `ENOSPC` は、可能な範囲でのクリーンアップを伴う `disk_capacity_exhausted` の失敗結果にマッピングされ、不完全な成果物を公開しない。ローカルアダプターは、ファイルシステムへの書き込みが可能ならクリーンアップ後にその失敗を永続化する。ストレージの枯渇・書き込み不可が続く場合、結果ファイルは保証できない。

将来の公開サービスは、クォータ・ボリューム制限、プロセスツリー全体のキャンセル、領域の確実な回収によって、ジョブプロセスの外側からストレージ上限を強制しなければならない。ポーリングやその高頻度化は、これらの制御の代わりにはならない。

エンジンは、ジョブ間の公平性や分離を保証しない。サービス・ワーカー poolは、1つのジョブが別ジョブのワークスペースを読んだり、共有リソースを無制限に使ったりできないようにしなければならない。

## 10. 病的な入力と展開による増幅

バイト・ページ・ピクセルチェックは一般的な増幅要因を減らすが、PDF パーサー・レンダリングの計算量を完全には制限しない。たとえば、深く入れ子になったオブジェクト、圧縮ストリーム、病的なベクター内容、ネイティブライブラリの例外的なケースがある。

したがって、次を適用する。

- 事前検証は、同じ制約付きワーカー・コンテナの信頼境界内で実施する。
- レンダリング・推論をvalidatorの代わりにしてはならない。
- 将来の公開サービスワーカーは、事前検証成功後にもdeadline/CPU/RAM/ディスク制限を強制しなければならない。
- ワーカーの強制終了は、有効な最終保護策である。
- 不完全なファイルが残っていても、強制終了された試行は非成功となる。

成功結果を得るためだけに、制限を回避してレンダリング DPIを黙って切り替えたり、要求ページを飛ばしたり、モデル品質を下げたり、detector/MMRの意味を変更したりしてはならない。

## 11. クリーンアップと公開

クリーンアップ・公開については、引き続き #337を正とする。

Issue #338による拒否では、次を適用する。

- 決定的な事前検証失敗後に、不要なGPU・モデル推論を起動しない。
- 最終/レビュー成果物を提示しない。
- エンジン所有のステージング・一時ファイルを可能な範囲で削除する。
- 信頼された運用者方針に従い、上限付きの診断情報だけを保持する。
- エンジン所有の試行ワークスペース外にある、不変の呼び出し側・入力元の入力を削除してはならない。
- プロセスが強制終了された場合、後の隔離・削除は外側のワーカーが担う。

内部ファイルの存在は公開を意味しない。

## 12. 実装状態

Issue #338は、再利用可能な検証・方針の層を導入した。現在の `PipelineJobExecutor` は、設定起点のパイプラインより前に事前検証を呼び、終端の失敗をv1結果へマッピングする。ローカル結果の永続化は、パイプラインランナーではなく `docker.distribution_job` が担う。

現在実装済みのもの:

- 上限付きローカルPDF バイト読み込みとSHA-256
- 不正・暗号化PDFの分類
- ページ選択とレンダリング前の寸法・ピクセル制限
- 絶対パスを含まない検証済みメタデータ
- ローカルパス・ルート・トラバーサル・URL・シンボリックリンクチェック
- 呼び出し側の `output_name` のファイル名ステム検証
- v1 `EngineError` へのマッピング
- 実装済み挙動の対象別テスト

引き続き将来の本番 `JobExecutor`・ワーカーアダプターが担うもの:

- 試行ごとの強制的なファイルシステム・コンテナクォータの設定・強制
- CPU/RAM/VRAM/ファイルシステム/コンテナの強制制御
- ワーカー・コンテナレベルでの外向きネットワーク方針の強制
- #337のプロセスグループ終了の統合

これらの統合は、現在のdetector/MMR/番号付けの精度契約を維持しなければならない。実際に本番実行経路を変える際は、ランタイム・GPU検証を行うべきである。
