このドキュメントでは、ローカル自動化および手動の PR 作業において実行すべき検証の選択方法を定義します。これは単なる任意のヘルパースクリプトよりも意図的に厳格に設計されており、自動化によってスキップされた検証を可視化し、スコープの逸脱（スコープドリフト）を早期に検知することを目的としています。

## 原則

- 実行環境の都合ではなく、変更された挙動に合わせて検証を選択すること。
- まず軽量なチェックから開始し、差分が実行時の挙動に影響を与え得る場合はスモークテストまたはフル評価を追加すること。
- チェックのスキップは、その理由が記録されている場合にのみ許容される。
- 評価に影響する（evaluation-sensitive な）変更には、裏付けとなる評価アーティファクト、または評価をスキップもしくは延期するという人間による明示的な判断のいずれかが必要である。
- Web またはクラウド環境のみでの編集は、GPU、Docker、データセット、またはフルパイプラインの挙動に対する最終的な検証とはならない。
- 評価に影響する実行を行う前に、PASS/FAIL を判定する受け入れ基準、主要メトリクス、対象データセット／入力セット、およびリグレッションゲートを特定すること。
- 結果を確認した後にそれらの基準を変更し、元の実行が合格したかのように記述しないこと。元の契約（コントラクト）で明示的に許容されていない限り、結果確認後のメトリクス／データセット／設定／許容誤差（tolerance）／シード（seed）／フィルタの変更は新たな評価として扱う。
- 別のメトリクスが改善した場合であっても、元の契約に対するリグレッションを報告すること。

## 検証ステータスとエビデンス

PR や完了報告では、チェックごとに 1 行を使用してください。テスト対象のリビジョンや環境が複数行で同一である場合は、レポート全体としてまとめて記載しても構いません。以下の 4 つのステータスを明示的に記録してください。

| ステータス | 今回の試行における意味 |
| --- | --- |
| Passed / 今回実行して成功 | チェックが最後まで実行され、受け入れ条件を満たした。 |
| Failed / 今回実行して失敗 | チェックが実行され、テスト／アサーションまたは受け入れ条件の失敗が報告された。 |
| Blocked / 実行できず | 前提条件、権限、環境、またはランチャーの失敗により完了できなかった。テスト結果は不明または部分的である。 |
| Not run / 未実行 | チェックは試行されなかった。スキップまたは延期された理由を説明すること。 |

ランチャーの非ゼロ終了コードだけでは、テストが失敗したことにはなりません。たとえば、pytest の開始前に `artifacts/test_fast.log` を開けなかった場合は **Blocked** であり、テストスイートの失敗ではありません。環境の不具合が発生する前にテストが部分的に実行された場合は、その部分的な件数を記録した上で、未完了のチェックとして Blocked のままにしてください。既存のログファイルから成功を推測してはなりません。

試行したすべてのチェックについて、以下を記録してください。

- テスト対象のコミット（`git rev-parse HEAD`）、またはベースコミットに加えて特定可能な未コミット差分（たとえば保存されたパッチとそのダイジェスト）。チェックの後にファイルが変更された場合は、そのチェックが最終的な差分を引き続きカバーしているかどうかとその理由を明記し、影響を受ける挙動が変化した場合は再実行すること。
- 正確なコマンド、作業ディレクトリ、および関連する環境（ホストのインタープリタまたは Docker イメージ ID、コンテナ、チェックアウトのマウント先）。関連する場合は設定や入力も記録すること。
- ステータス、取得可能な場合は終了コード（取得できない場合はその理由を説明）、およびログ／アーティファクトのパスまたは簡潔な出力。Blocked の場合は、試行したコマンド、具体的なエラー、および代替として完了したチェックとその限界を含めること。Not run の場合は、その理由と必要なフォローアップを含めること。

過去の結果は、**Historical evidence**（過去のエビデンス）とラベル付けした別の段落に記載し、元のリビジョン、環境、コマンド、および利用可能な場合はエビデンスの参照先を添えてください。それらが今回の変更に対して再実行されたものではないことを明記し、来歴（provenance）が欠落している場合は不明のままとして扱うこと。過去のコミット、別の worktree、CI、または別の環境での合格は、今回の再実行の証明にはなりません。ブロックされたチェックが後に再試行されて成功した場合は、それぞれの試行を個別に保持してください。

利用できないツールの選択や別のチェックアウトに対するテストを防ぐため、実行前に [environment preflight](../ENVIRONMENTS.md#execution-preflight) に従ってください。

例（説明用の例であり、実際の検証結果ではありません）：

テスト対象：コミット `<sha>` および保存された `logs/issue<N>/validation/<run>/changes.patch`（SHA-256 `<digest>`）。作業ディレクトリ：`<container>` 内の `/workspace`、イメージ `<image-id>`、アクティブな worktree を同パスにマウント。

| チェック | 今回のステータス | コマンド / エビデンス |
| --- | --- | --- |
| Focused pytest | Passed | `docker exec -w /workspace -e PYTHONPATH=/workspace <container> /opt/venv_pipeline/bin/python -m pytest tests/test_python_env.py`; exit 0, `<run>/pytest.log`. |
| Fast tests | Blocked | 試行内容：`docker exec -w /workspace <container> make test-fast PYTHON=/opt/venv_pipeline/bin/python`; exit 2, pytest 開始前に `artifacts/test_fast.log: Permission denied`。再試行時は、まず `mapfile -t fast_tests < <(sed -n 's/^FAST_TESTS ?= //p' Makefile | tr ' ' '\n')` で管理対象のターゲット一覧を読み込み、その後 `docker exec -w /workspace -e PYTHONPATH=/workspace <container> /opt/venv_pipeline/bin/python -m pytest "${fast_tests[@]}"` を実行する必要がある。上記の Focused pytest は選択されたモジュールのみをカバーしている。 |
| GPU smoke | Not run | ドキュメントのみの変更であり、実行時の挙動に変更はないため。 |

Historical evidence：fast tests は `<other-environment>` 上の `<older-sha>` で合格済み（コマンドおよびログ：`<reference>`）。今回のターゲットに対しては正常に再実行されていない。
完了した実行中にアサーションが失敗した場合は、**Failed** とその失敗の概要を記録してください。

## 評価契約の完全性（インテグリティ）

精度、品質、互換性、またはパフォーマンスに関する主張の根拠として使用されるすべての実行について、以下を遵守してください。

1. 結果を解釈する前に契約（コントラクト）を記録すること：受け入れ基準、主要メトリクス、データセット／入力の範囲、閾値／許容誤差（tolerances）、関連する場合はシード（seed）、ベースライン／正準（canonical）ターゲット、および必須のリグレッションゲート。
2. 同等の入力に対して、その契約に基づき候補（candidate）を評価すること。
3. 改善したメトリクスだけでなく、すべての必須ゲートを報告すること。
4. 必須ゲートが 1 つでも失敗した場合、その実行はその契約下において不合格（failure）となる。目標の名前を変更したり、より有利なメトリクスに切り替えたり、失敗したケースを除外したり、データセットを絞り込んだり、無関係な閾値を再調整したりした上で、元の結果があたかも精度を維持していたかのように記述してはならない。
5. 元の契約またはテストハーネスに誤りがあったことがエビデンスによって示された場合は、古い結果を保持したまま欠陥を説明し、修正された契約を定義した上で、明確にラベル付けされた新しい評価を実行または再スコア付け（rescore）すること。修正された結果は、修正後の契約に対してのみ古い結果を置き換えるものであり、過去の実行を遡って合格にするものではない。

## センシティブな変更の検出

ローカルの検証スクリプトは差分を検査し、変更カテゴリを報告する必要があります。少なくとも、以下のパスまたは用語はセンシティブ（要注意）として扱われます。

- `configs/`
- `src/pipeline/`
- `tools/issue120/`
- `experiments/`
- `Dockerfile`
- `requirements.txt`
- `pyproject.toml`
- `Makefile`
- `threshold`、`seed`、`dataset`、`metric`、`evaluation`、`baseline`、`canonical`、`filter`、`detector`、`orchestrator`、または `route` に言及しているファイルまたは差分

センシティブな項目に一致したからといって、必ずしもその PR が誤っているとは限りません。これは、どのより強力なチェックを実行したか、あるいはなぜそれらをスキップしたのかをレポート内で説明しなければならないことを意味します。

## ローカルでのフル評価の承認

フル評価は引き続き人間が管理する検証レベルですが、ユーザーまたは Issue によって明示的に承認された後は、その PR について再度確認することなくローカルの自動化処理からフル評価を開始できます。結果のレポートには、コマンド、コミット、設定／データ入力、終了ステータス、およびログパスを含める必要があります。

## PR サマリーに求められる内容

軽微ではない PR や検証コメントには、以下の内容を含める必要があります。

- 変更したファイルとその意図。
- 検出された変更カテゴリ。
- このポリシーに従って求められる検証。
- 実際に実行したコマンド。
- ログパスと終了コード。
- スキップした必須または推奨チェックと、その正確な理由。
- 評価に影響する作業の場合：代替の成功基準にすり替えることのない、元の評価契約、ベースライン、候補（candidate）の結果、ゲートごとの差分（delta）、および PASS/FAIL。
- 残存するリスクおよび依然として必要な人間による判断。
