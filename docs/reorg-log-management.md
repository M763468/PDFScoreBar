# ログ・成果物管理ガイドライン

このドキュメントは、プロジェクト内のログおよび中間成果物が無秩序に増加するのを防ぎ、`git worktree` 等の並列環境でも整合性を保つための運用ルールを定めたものです。

## 1. ディレクトリ構造の原則

全ての実行出力およびデバッグ用アセットは、原則として `logs/` ディレクトリ配下に集約します。従来の `debug_outputs/` や `output/` は廃止されました。

### 1.1 カテゴリ分類
`logs/` 直下に以下のサブディレクトリを作成し、用途に応じて使い分けます。

- `logs/runs/`: パイプライン（`src/pipeline/main.py`）の通常実行結果。
- `logs/eval/`: ベンチマーク評価や精度検証の結果。
- `logs/experiments/`: 新機能やアルゴリズムのプロトタイプ実験。
- `logs/models/`: CNN 等の学習済みモデル（`.pth`）および学習履歴。
- `logs/system/`: システムレベルのログ（コンテナ起動ログ、リソース監視等）。

### 1.2 ディレクトリ命名規則
追跡を容易にするため、以下の形式でディレクトリを作成します。

`logs/<category>/<task_id>_<timestamp>/`

例: `logs/eval/issue90_20260314_180000/`

## 2. Worktree における共有・独立ポリシー

並列実行環境（`git worktree`）では、データの整合性を守るために以下のルールを適用します。

### 2.1 共有 (Shared)
以下のパスは、全 worktree で共通のストレージ（またはマウント）を参照し、読み取り専用として扱います。
- `data/`: 元データ（PDF、画像、GT）。
- `datasets/`: 学習用データセット。
- `logs/models/`: 最新の公式モデル（例: `cnn_classifier_best.pth`）。

### 2.2 独立 (Isolated)
以下のパスは、worktree ごとに個別のディレクトリを持ち、実行結果が混ざらないようにします。
- `logs/runs/`, `logs/eval/`, `logs/experiments/`: 実行ごとに新しいディレクトリが生成されるため、独立させる。
- `artifacts/`: 一時的な検証ログや triage 結果。

## 3. クリーンアップ運用

### 3.1 手動クリーンアップ
不要になった過去の実験ログは、適宜 `logs/archive/` に移動するか削除します。

### 3.2 自動化支援
`Makefile` に以下のターゲットを導入し、不要なファイルの蓄積を抑制します。

- `make clean-logs`: 30日以上前の `logs/runs/` を一括削除（検討中）。
- `make check-consistency`: `MANIFEST.md` に記載のない「迷子（Orphan）」ディレクトリを警告。

## 4. ドキュメントとの同期

新しい評価や実験を行った際は、必ずそのディレクトリパスを `DEVELOPMENT_LOG.md` または関連する Issue 報告書に記録してください。パスが明記されていないディレクトリは、将来のクリーンアップ対象（削除候補）とみなされます。
